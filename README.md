# Feedback intelligence: themes, sentiment shifts, service priorities

Python project that builds a synthetic feedback dataset (survey responses,
reviews and support messages) and analyses it for recurring themes, sentiment
shifts over time and ranked service priorities.

All of the data is generated by the code here. Nothing external, nothing real.

## Running it

```
python -m venv .venv && source .venv/bin/activate   # optional
pip install -r requirements.txt                      # only needed for the tests

python src/generate.py --scale full --out data/full   # 50,000 feedback records + 20,000 support messages
python src/analyze.py  --data data/full               # writes data/full/outputs/
python src/validate.py --data data/full               # 41 checks, exit 0 means no unexpected failures
python -m pytest tests/ -q
```

There is also a small `starter` scale (500 feedback + 240 messages) that runs
the same code for quick iteration:

```
python src/generate.py --scale starter --out data/starter
```

To check reproducibility, regenerate with the same seed and compare:

```
python src/generate.py --scale full --out /tmp/full-again
python src/validate.py --data data/full --compare /tmp/full-again
```

## How it fits together

`src/generate.py` creates the master data first (customers, products,
channels, surveys, themes, sentiment labels), then the records that depend on
it (survey responses, reviews, support tickets and their messages), so every
foreign key points at a real parent row. Sentiment scores are copied from the
label catalogue rather than drawn randomly.

Labels are sampled, not assigned at random: the theme depends on the product
category, and the sentiment depends on the theme. On top of that there are two
deliberate trend events (next section), which is what makes the sentiment
shifts in the output explainable instead of noise.

`src/textgen.py` builds the text itself from an opening, a theme-specific
aspect phrase and a closing, picked by sentiment, so the text and its label
match. About 5% of feedback is sarcastic, about 6% is in another language
(Hindi, Marathi, Spanish, German, French), and `mixed` records deliberately
pair a positive and a negative aspect.

`src/analyze.py` reads the dataset and writes the outputs listed below. Two
things it is careful about: it only reads a fixed whitelist of columns (the
dataset contains a leaked `test_label` column on some rows and it is never
used), and it excludes every record listed in the ground truth file.

`src/validate.py` checks the dataset: primary keys, foreign keys, allowed
values, date ordering, row counts against the manifest, duplicate groups
against the labelled duplicates, and checksum reproducibility. Foreign keys
that dangle are expected for exactly one anomaly type (see below) and are
reconciled against the ground truth instead of being passed silently.

## The two trend events

- A bad Mobile App update on 2026-03-15: Technical Issues volume for that
  product roughly triples and sentiment drops from March to May 2026, then
  recovers. Shows up in `outputs/sentiment_shifts.csv`.
- A support improvement programme starting 2026-07-01: the negative share of
  Support Responsiveness falls from about 25% overall to about 17.5% in
  Aug-Oct. Shows up in `outputs/theme_summary.csv` and
  `outputs/service_priorities.csv`.

## Outputs (`data/full/outputs/`)

| File | Contents |
|---|---|
| `theme_summary.csv` | Volume, share and sentiment mix per theme |
| `sentiment_shifts.csv` | Monthly sentiment index per product and theme, with the Q1 to Q2 shift |
| `service_priorities.csv` | Themes ranked by recent negative volume x recent negative share |
| `action_items.csv` | Themes over 2% of feedback and 30% recent negative share, turned into action items with the counts that triggered them |
| `action_item_events.csv` | Lifecycle history of the action items |
| `metrics.json` | Label distribution, plus a simple keyword classifier scored against the labels (accuracy about 0.73; it never predicts `mixed`, which the output says openly) |
| `validation_summary.md` / `.json` | The 41 validation checks with details |

On the full dataset, Technical Issues comes out as the top service priority
(60% negative, 1,178 negative records since August), then Pricing & Value and
Delivery & Timeliness. Four action items are generated.

## Data model

10 entities: Customer, Product, Channel, Survey, SurveyResponse, Review,
SupportTicket, SupportMessage, Theme, SentimentLabel, plus the ActionItem
outputs. `docs/data_dictionary.md` describes every field and `schema.sql` has
the DDL.

IDs are deterministic: `SUR-2026-000001`, `RESP-<survey-id>-001`,
`REV-2026-000001`, `MSG-<ticket-id>-001`, `THEME-000001`. The seed is fixed at
20261022 and the scale is just a parameter, so the starter and full datasets
come out of the same generator. Lifecycle changes are appended to
`state_events.csv`, never overwritten.

## Edge cases

After the clean baseline is generated, five kinds of deliberate problems are
injected and written to `ground_truth.csv` / `ground_truth.json`. They are
test data for the validator and the analysis, never inputs to either.

| issue_type | Count (full) | Notes |
|---|---|---|
| `label_contradicts_text` | 150 | Label flipped with no explanation; excluded from metrics |
| `duplicate_response` | 120 | Exact copy of an existing response under a new ID |
| `customer_identity_leaked` | 100 | Fake email/phone inside support text (example domains and numbers only) |
| `theme_outside_taxonomy` | 80 | `THEME-999999`, not in the taxonomy; the validator expects exactly these dangling keys |
| `test_label_in_input` | 100 | `test_label` column filled in; analysis never reads it |
